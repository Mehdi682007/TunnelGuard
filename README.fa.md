## دریافت و نصب

**جدید در ۲.۳: [عیب‌یابی، ارتقا و بازگشت، حذف، تمدید خودکار دو سمت و آزمایش مداوم/میدانی](OPERATIONS.fa.md)**. دستورهای عملی و محدوده تست‌ها در راهنمای نگهداری آمده است.

**جدید در ۲.۲: [نصب خودکار Spoof در دو سمت](SPOOF.fa.md)**، همراه دانلود هسته، لایه رمز‌شده و افزودن مسیر به نگهبان قبلی. این قابلیت مبتنی بر هسته بتا و آزمایشی است؛ IP مبدأ و شبکه میزبان سازگار لازم دارد.

روی Ubuntu 24.04:

```bash
sudo apt update
sudo apt install -y git python3 curl
git clone https://github.com/Mehdi682007/TunnelGuard.git
cd TunnelGuard
python3 tunnelguard.py demo --config config.multilayer.example.json
```

سپس `http://127.0.0.1:8787` را در مرورگر باز کنید. برای نصب محلی اختیاری بدون root:

```bash
python3 install.py
export PATH="$HOME/.local/bin:$PATH"
tunnelguard demo
```

نصاب فایل‌های برنامه را در `~/.local/share/tunnelguard` و فرمان اجرا را در `~/.local/bin/tunnelguard` می‌گذارد؛ تنظیمات شخصی موجود را بازنویسی نمی‌کند و سرویس، فایروال یا route سیستم را تغییر نمی‌دهد. برای حفظ PATH بعد از بستن ترمینال، خط export را به پروفایل shell خودتان اضافه کنید. برای ارتقا، از پوشه نسخه جدید دوباره `python3 install.py` را اجرا کنید. برای حذف، بعد از پشتیبان‌گیری تنظیمات، فایل فرمان و پوشه نصب را که نصاب چاپ می‌کند حذف کنید.

روی ویندوز، پس از نصب Python 3.11+ و Git، مخزن را دریافت و به‌جای `python3` از `python` استفاده کنید؛ نصاب اختیاری مخصوص Linux/macOS است. فایل ZIP صفحه Releases هم قابل استخراج و اجراست. برای حالت واقعی curl نسخه 8.4+ باید در PATH باشد.

نسخه **2.1.0**: [نصب خودکار دو سمت و دانلود هسته](DEPLOY.fa.md) برای Shadowsocks 2022، Trojan/TLS و Hysteria2/QUIC اضافه شد. داشبورد فارسی و راست‌به‌چپ با انتخاب زبان English/فارسی است. زبان انتخابی در همان مرورگر ذخیره می‌شود؛ گزارش HTML ذخیره‌شده هم دوزبانه است و به اینترنت نیاز ندارد. نام مسیرها و فیلدهای JSON برای سازگاری فنی انگلیسی باقی می‌مانند.

دو مسیر آماده دارید؟ این ابزار سلامت واقعی آن‌ها را اندازه می‌گیرد و برای **اتصال‌های TCP جدید**، یک خروجی SOCKS5 ثابت با مسیر پشتیبان می‌سازد. داشبورد زنده، نمودار پاسخ HTTP، تاریخچه تغییر مسیر، آزمایش سرعت و خروجی HTML/JSON دارد.

**مدیریت مسیرهای موجود و نصب سه مسیر تازه:** برای نصب دو سمت از [deploy.py](DEPLOY.fa.md) استفاده کنید. برای سایر هسته‌ها، TunnelGuard روی سیستمی اجرا شود که خروجی HTTP CONNECT یا SOCKS5 هر مسیر در دسترس است. صرف تغییر نام یا پورت یک مسیر، پشتیبان مستقل ایجاد نمی‌کند.

راهنمای قابلیت‌های جدید: [مدیریت چندلایه، Spoof، پروفایل‌ها و هسته‌ها](MULTILAYER.fa.md). این نسخه ۱۰ آداپتر اجرای هسته خارجی، انتخاب دستی مسیر، سیاست کیفیت، مهلت تثبیت مسیر نوسانی، فوروارد TCP و ثبت رخداد JSONL دارد. باینری‌های هسته داخل بسته نیستند؛ نصب سمت سرورها خودکار نشده است.

## شروع سریع: دمو بدون سرور

نیاز: Python 3.11 یا جدیدتر. دمو حتی curl و اینترنت هم لازم ندارد.

```bash
python3 tunnelguard.py demo
```

داشبورد را در `http://127.0.0.1:8787` باز کنید. مسیر A در ثانیه ۱۲ خراب و در ثانیه ۳۰ بازیابی می‌شود؛ چرخه هر ۴۸ ثانیه تکرار می‌شود. بعد از چند نمونه، تغییر مسیر را می‌بینید. **تمام اعداد دمو ساختگی‌اند، برچسب SIMULATION نمایش داده می‌شود و خروجی پروکسی در دمو فعال نیست.**

در ویندوز به‌جای `python3` از `python` استفاده کنید.

## استفاده واقعی

پیش‌نیاز اجرا: Python 3.11+ و curl 8.4+. هیچ پکیج pip لازم نیست. روی Ubuntu 24.04:

```bash
sudo apt update
sudo apt install python3 curl
python3 tunnelguard.py init
nano config.json
python3 tunnelguard.py check --config config.json
python3 tunnelguard.py run --config config.json --output reports
```

مقدار `proxy` در هر مسیر را با خروجی واقعی همان مسیر جایگزین کنید:

```json
{"name": "Route-A", "proxy": "socks5h://127.0.0.1:1080", "priority": 10}
```

```json
{"name": "Route-B", "proxy": "http://127.0.0.1:2080", "priority": 20}
```

یا به‌جای ویرایش دستی، از راه‌اندازی مرحله‌به‌مرحله استفاده کنید:

```bash
python3 tunnelguard.py init --interactive
```

نام انگلیسی، آدرس پروکسی، برچسب لایه و نوع هسته هر مسیر پرسیده می‌شود. برای مسیر از قبل اجراشده، نوع هسته را external بگذارید. ورودی آدرس عمداً مخفی است تا رمز احتمالی جلوی دوربین یا در تاریخچه ترمینال نماند. اولویت مسیرها به‌ترتیب ورود تعیین می‌شود. فرمان init فایل موجود را بازنویسی نمی‌کند؛ برای فایل دیگر از `--output another-config.json` استفاده کنید و همان مسیر را در فرمان run با `--config` بدهید. در لینوکس فایل با دسترسی 600 ساخته می‌شود.

فرمان‌های واقعی ابتدا `config.json` کنار اسکریپت را می‌خوانند؛ اگر وجود نداشته باشد، نمونه را استفاده می‌کنند. دمو همیشه به‌صورت پیش‌فرض تنظیمات نمونه را می‌خواند. `--config` انتخاب صریح شماست.

برای پیام‌های انگلیسی ترمینال:

```bash
python3 tunnelguard.py run --lang en --config config.json
```

برای خروجی صرفاً انگلیسی از --lang en استفاده کنید. زبان پیش‌فرض پیام‌های برنامه فارسی است. کدهای فنی وضعیت، نام گزینه‌ها و بعضی جزئیات اعتبارسنجی برای عیب‌یابی انگلیسی می‌مانند. زبان ترمینال مستقل از دکمه زبان داشبورد است.

عدد priority کوچک‌تر یعنی ترجیح بالاتر. پروکسی HTTP باید CONNECT را برای پورت مقصد مجاز کند. HTTP Basic و SOCKS5 username/password پشتیبانی می‌شوند؛ فرمت `scheme://user:password@host:port` است. کاراکترهای ویژه نام کاربری و رمز را percent-encode کنید. فایل کانفیگ را خصوصی نگه دارید؛ در لینوکس `chmod 600 config.json`.

در مرورگر یا برنامه مصرف‌کننده، SOCKS5 را روی **127.0.0.1:1088** بگذارید و DNS از طریق SOCKS را فعال کنید. تست از ترمینال:

```bash
curl --noproxy "" --proxy socks5h://127.0.0.1:1088 https://example.com
```

فقط برنامه‌هایی که از این خروجی استفاده می‌کنند تحت مدیریت TunnelGuard هستند. این ابزار route سیستم، فایروال، DNS سیستم یا تنظیمات کلاینت VPN را تغییر نمی‌دهد. خود خروجی‌های بالادستی نباید به پورت 1088 برگردند.

اگر روی VPS اجرا می‌کنید، دسترسی محلی را از کامپیوتر خودتان فوروارد کنید:

```bash
ssh -N -L 8787:127.0.0.1:8787 -L 1088:127.0.0.1:1088 user@YOUR_SERVER
```

هر دو listener عمداً فقط روی loopback باز می‌شوند؛ این نسخه endpoint عمومی یا سرویس چندکاربره نیست.

## منطق نگهبان

- هر ۵ ثانیه، یک درخواست GET کوچک به هر هدف **از داخل هر مسیر** ارسال می‌شود. TLS بررسی می‌شود؛ redirect دنبال نمی‌شود. کد پاسخ باید با تنظیمات هدف منطبق باشد.
- در تنظیم نمونه، موفقیت حداقل یکی از دو هدف کافی است (`quorum: 1`). برای الزام موفقیت هر دو، مقدار را ۲ کنید. هدف‌ها را مطابق کاربرد و شبکه خودتان انتخاب کنید؛ خرابی مقصد می‌تواند شبیه خرابی مسیر دیده شود.
- مسیر پس از ۲ دور موفق UP و پس از ۳ دور ناموفق DOWN می‌شود. قبل از تأیید اولین مسیر، خروجی بسته است. با تنظیم پیش‌فرض و خرابی کامل، تشخیص معمولاً حدود ۱۰ تا ۱۹ ثانیه طول می‌کشد؛ تضمین زمانی نیست.
- با خرابی مسیر فعال، سالم‌ترین گزینه طبق **اولویت تنظیم‌شده** انتخاب می‌شود؛ زمان پاسخ فقط برای تساوی اولویت کاربرد دارد. امتیاز مبهم یا تضمین «سریع‌ترین مسیر» نداریم.
- بازگشت خودکار به مسیر با اولویت بهتر به‌صورت پیش‌فرض خاموش است تا نوسان کم شود. `failback: true` آن را روشن می‌کند؛ `cooldown` حداقل فاصله بازگشت است و جلوی خروج اضطراری از مسیر خراب را نمی‌گیرد.
- اندازه‌گیری قدیمی‌تر از `stale_after` معتبر نیست. در نبود مسیر سالم، اتصال جدید رد می‌شود؛ هیچ fallback مستقیم به اینترنت نداریم.
- اتصال برقرارشده روی همان مسیر باقی می‌ماند. تماس یا دانلود در حال اجرا با جابه‌جایی به‌صورت جادویی منتقل نمی‌شود. برنامه مصرف‌کننده باید در صورت قطع، دوباره متصل شود. از نسخه ۲، اگر برقراری اتصال قبل از ارسال داده شکست بخورد، مسیر سالم دیگر امتحان می‌شود. داده برنامه که قبلاً ارسال شده، بازپخش نمی‌شود؛ اتصال‌های موجود هم منتقل نمی‌شوند.

## آزمایشگاه و تست سرعت

گزارش چند دور سلامت:

```bash
python3 tunnelguard.py lab --config config.json --rounds 5 --output reports
```

فایل `reports/report.html` را باز کنید؛ مستقل از برنامه و بدون CDN کار می‌کند. گزارش ذخیره‌شده، snapshot است. JSON برای تحلیل یا ساخت محتوای ویدئو هم تولید می‌شود. فرمان lab هنگام نبود مسیر تأییدشده exit code برابر ۲ می‌دهد؛ تعداد rounds را کمتر از recovery نگذارید.

دورهای آزمایشگاه با فاصله `interval` اجرا می‌شوند تا نوسان در طول زمان دیده شود. گزارش‌های دوره‌ای به‌صورت جایگزینی اتمی ذخیره می‌شوند؛ باز کردن فایل هنگام ذخیره، محتوای نیمه‌نوشته نشان نمی‌دهد. اجرای هم‌زمان چند برنامه باید پوشه گزارش و پورت‌های متفاوت داشته باشد.

بنچمارک دانلود، با فایل کوچک و اندازه مشخص روی سرور خودتان:

```bash
python3 tunnelguard.py benchmark --config config.json \
  --url https://YOUR_DOMAIN/test-5MiB.bin \
  --max-bytes 5242880 --timeout 20 --rounds 3 --output reports
```

به‌جای آدرس نمونه، URL واقعی فایل خودتان را بگذارید. اندازه فایل باید حداکثر برابر cap باشد. مسیرها به‌ترتیب تست می‌شوند تا با هم روی لینک رقابت نکنند. دانلود ناقص، timeout، HTTP نامعتبر و عبور از سقف اندازه، **نتیجه موفق سرعت محسوب نمی‌شوند**. خروجی در `benchmark.json` است؛ داشبورد نمودار سرعت دانلود ندارد. این سنجش سرعت انتقال فایل کوتاه است و برآورد قطعی ظرفیت مسیر نیست.

هر بررسی سلامت سقف پاسخ ۶۴ KiB و timeout دارد. با ۲ مسیر، ۲ هدف و فاصله ۵ ثانیه، حدود ۴۸ درخواست کوچک در دقیقه ارسال می‌شود. بنچمارک فقط با فرمان صریح شما اجرا می‌شود. سقف حجم به رفتار نسخه curl هم وابسته است؛ حداقل نسخه لازم 8.4+ است و هنگام شروع بررسی می‌شود، و هدرها/سربار شبکه جزو سقف payload نیستند.

## معنی اعداد و حریم خصوصی ضبط

- HTTP TIME: زمان کامل درخواست HTTP؛ **پینگ ICMP نیست**.
- VARIATION: میانگین اختلاف مطلق زمان پاسخ نمونه‌های موفق متوالی؛ jitter شبکه یا packet loss نیست.
- SUCCESS: درصد دورهای موفق در پنجره حداکثر ۱۲۰ دور؛ معیار uptime بلندمدت نیست.
- هنگام شکست، ستون HTTP TIME آخرین زمان پاسخ موفق را نگه می‌دارد؛ LAST ISSUE و فاصله نمودار شکست را نشان می‌دهند.
- SESSION UPTIME: زمان روشن بودن برنامه، نه درصد دسترس‌پذیری.
- اطلاعات کانفیگ، IP بالادستی، رمز و URL هدف‌ها در داشبورد یا گزارش قرار نمی‌گیرند. نام مسیرها نمایش داده می‌شود؛ برای ضبط از نام‌های خنثی استفاده کنید. `config.json` را جلوی دوربین باز نکنید.
- ابزار داده‌ای به سرویس تحلیل یا تله‌متری ارسال نمی‌کند؛ تنها درخواست‌های هدف و ترافیک مصرف‌کننده از مسیرها عبور می‌کنند.

## اجرای دائمی در لینوکس، اختیاری

نمونه `tunnelguard.service` برای نصب در `/opt/tunnelguard` ارائه شده است. بعد از تست کانفیگ:

```bash
sudo mkdir -p /opt/tunnelguard
sudo cp tunnelguard.py engines.py dashboard.html config.json /opt/tunnelguard/
sudo chmod 600 /opt/tunnelguard/config.json
sudo cp tunnelguard.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tunnelguard
sudo journalctl -u tunnelguard -f
```

برای توقف: `sudo systemctl disable --now tunnelguard`. برای حذف سرویس: فایل `/etc/systemd/system/tunnelguard.service` را حذف کنید و `sudo systemctl daemon-reload` بزنید. گزارش دوره‌ای در این سرویس خاموش است؛ از دکمه Export JSON استفاده کنید. سرویس با کاربر موقت محدود اجرا می‌شود و کانفیگ را از credential خصوصی systemd می‌خواند.

## وضعیت نسخه و تست‌ها

برنامه با کتابخانه استاندارد Python اجرا می‌شود؛ فایل engines.py نیز باید کنار اسکریپت باشد. تست‌های محلی شامل انتقال واقعی TCP از HTTP CONNECT و SOCKS5، خرابی بالادست و سوییچ، عدم اتصال مستقیم، اعتبارسنجی Host داشبورد، quorum و حذف اطلاعات حساس از گزارش هستند:

```bash
python3 -m unittest -v
```

تست خودکار روی Linux و Windows اجرا می‌شود؛ جزئیات و دامنه تست‌ها در [TESTING.md](TESTING.md) است. اپراتورهای ایران و بار تولید نیاز به آزمایش میدانی دارند. نصب خودکار سه پروتکل در [راهنمای نصب](DEPLOY.fa.md) آمده است. حامل QUIC پشتیبانی می‌شود، اما UDP برنامه‌های مصرف‌کننده، TUN سیستم و انتقال اتصال‌های جاری پشتیبانی نمی‌شوند. برای VLESS و مشابه آن، خروجی محلی SOCKS/HTTP کلاینت آن‌ها را معرفی کنید.

منابع فنی: [curl manual](https://curl.se/docs/manpage.html)، [Python asyncio streams](https://docs.python.org/3/library/asyncio-stream.html).
